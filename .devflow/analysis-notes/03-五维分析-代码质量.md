# M3 素材：代码质量维度分析

## 重复代码

### 1. Import / ImportConcurrent 双份分发（importer.go:41-148）
- `Import`（41-81）与 `ImportConcurrent`（83-148）的 `switch f := e.(type)` 分发结构高度重复：
  - 相同 default 分支：`name := defaultSheetName` + `WithSheetName` 断言 + `resolveSheetName` + `i.imp`（Import:50-62 vs ImportConcurrent:91-104，逐行一致）
  - 相同 `WithMultipleSheets` 分支：遍历 `f.Sheets()`（Import:64-73 vs ImportConcurrent:110-131）
  - 相同 `defer i.Close()`、相同 `if i.reader == nil` 守卫
- 差异仅在并发分支多了 `workers`/`errChan`/`sem`/`wg` 调度逻辑。
- 可合并判断：default 分支（单 sheet 分发）逻辑可抽为 `i.importSingle(e)`，两个入口共用；WithMultipleSheets 的 sheet 名解析逻辑（`WithSheetName` 覆盖 map key）也重复（Import:66-68 vs ImportConcurrent:116-119）。

### 2. nil reader 守卫重复
- `importer.go:44-46` 与 `importer.go:86-88`：相同的 `if i.reader == nil { return fmt.Errorf("reader is not initialized") }`。
- `reader.go` 内部每个方法又有独立 nil 守卫：`withSkip`(33-38)、`GetRows`(42-43)、`GetHeader`(59-60)、`sheetExists`(97-98)、`firstSheetName`(109-110)、`resolveSheetName`(120-121)。
- 双层守卫：importer 层和 reader 层都检查 nil，属防御性冗余。

### 3. sqref 分割逻辑重复（exporter.go:82-85 vs dataValidate.go:85-89）
- `setColWidth`（exporter.go:82-85）与 `FormatDataValidate`（dataValidate.go:85-89）都有相同的 `strings.SplitN(idx, ":", 2)` + `len==1 则 append 自身` 的 sqref 展开逻辑。

## 命名 / 可读性

- `errors.go:1` 引入 `bytes`+`errors`+`fmt`+`reflect`+`strings` 多个包，但 `ExcelLineError`/`LinesError` 类型（105-130）在全库无任何引用（`grep` 验证），疑似历史遗留死类型。
- `InvalidUnmarshalError.Error()`（errors.go:16-25）错误信息硬编码 `"json: Unmarshal(...)"` 前缀——本库是 excelize 而非 json，属复制粘贴遗留，错误文案误导。
- 导入顺序：exporter.go:5 `"github.com/xuri/excelize/v2"` 与 `"strings"` 之间无空行分组（gofmt 已排序但 import 分组不规范，实为可读性小问题）。

## 分函数行数 / 嵌套深度
- `ImportConcurrent`（importer.go:83-148）约 66 行，超过"单函数 ≤50 行"建议，嵌套最深 3 层（switch→for→goroutine）临界。
- `fillStruct`（scanner.go:76-99）嵌套 3 层（for field → for header → if）。
- `FormatDataValidate`（dataValidate.go:81-104）switch 嵌套两层。
