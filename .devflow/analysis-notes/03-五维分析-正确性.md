# M3 素材：正确性维度分析

## 1. 边界条件逐项

### 1.1 空表 / 空文件
- `scanSlice`（scanner.go:319）`if len(rows) <= 1 { return nil }`：表头 + 无数据行时直接返回，不报错，切片保持零值——**行为正确**。
- `firstSheetName`（reader.go:112-115）：`len(list)==0` 返回错误"excel file does not contain any sheet"——**正确**。
- `resolveSheetName`（reader.go:119-127）：name 非空但 sheet 不存在时，**静默回退到 firstSheetName**（123-126），不报错。这会导致用户拼错 sheet 名时被静默导入到第一个 sheet，**潜在 bug**（应报 SheetError 或 ErrSheetNotExist，而不是静默回退）。

### 1.2 缺列 / 多余列
- `fillMap`（scanner.go:64-74）：`if j >= len(headers) continue` 处理了行比表头多的情况，但**表头比行多时**，缺失列会被当作空字符串（fillStruct 中 `cellValue` 保持零值 `""`）——行为是"缺列当作空值"，取决于 `default` 标签，若字段无 default 则填入零值，**语义模糊但非崩溃**。
- `fillStruct`（scanner.go:82-96）：外层遍历 fields，内层 `for i, header := range headers` 查找匹配列，若某字段 alias 在 headers 中不存在，则 `cellValue` 保持 `""`（零值），随后 `applyFieldRule` 用空字符串转换——**缺列不报错，静默填零值**，可能与用户预期不符（表头匹配校验只在校验 WithHeading 时触发，未实现 Headers() 的结构体完全无表头校验）。

### 1.3 类型不匹配
- `TypeConverter.ConvertToType`（scanner.go:16-38）：用 `cast.ToInt/ToInt64/ToFloat64/ToBool/ToString` 强转。**问题**：cast 对无法解析的字符串静默返回零值（例如 `cast.ToInt("abc")` = 0），**不报错**。类型不匹配被静默吞成零值，无错误提示。default 分支（33-37）对未知类型一律 `cast.ToString`，若目标字段是自定义类型（如 time.Time）会 panic 风险（`fieldValue.Set(string)` 到 time.Time 会 panic）。
- **严重**：`ConvertToType` 对 `reflect.Struct` 等未处理类型返回 string，`applyFieldRule`（scanner.go:142-143）直接 `fieldValue.Set(convertedValue)`，若目标字段类型与 string 不兼容会 panic。

### 1.4 嵌套结构
- `parse`（column.go:37-67）递归展开嵌套 struct。**问题**：`parse(v reflect.Value)` 先判断 `v.Kind() != reflect.Struct` 返回错误，但 `fillStruct`（scanner.go:54-61）在 `target.Kind()` 为 Map 时走 fillMap，Struct 走 fillStruct。嵌套 struct 字段（非指针）会被 `v.Field(i).Kind()==reflect.Struct` 递归 parse（column.go:43），但如果嵌套的是**指针 struct**（`*TermDictRow`），`Kind()==reflect.Pointer`，不会被递归展开，且无 xlsx tag 时被跳过——`TermDictRow` 的 `TermInfo *TermDictRow` 字段依赖 relation 标签而非递归 parse，恰好避开了。若用户有嵌套**值 struct**且无 tag，字段会被 silently 展开但可能产生未预期的字段（因为递归 parse 会 append 子字段）。

### 1.5 越界访问
- `scanSlice`（scanner.go:326-331）：`if i >= rv.Cap() rv.Grow(1)` + `if i >= rv.Len() rv.SetLen(i+1)`，通过 Cap/Len 检查避免越界。**潜在问题**：`rv.Grow(1)` 每次只 grow 1，对 10 万行，append 式逐次 grow 会导致反复扩容（cap 增长曲线是 Go slice 的 2 倍增长，但这里显式 Grow(1)+SetLen 每次都精确扩 1，可能触发大量底层 realloc）。这是性能问题（已列入性能维度），非正确性 bug，但 `SetLen` 后 `rv.Index(i)` 是合法的。

## 2. 错误路径

### 2.1 错误类型族触发匹配
| 错误类型 | 定义 | 触发点 | 匹配 |
|---------|------|--------|------|
| ValidateHeaderError | errors.go:27 | importer.go:154,158 | ✅（表头校验/读取失败） |
| HeaderLengthError | errors.go:52 | importer.go:187 | ✅（表头长度不匹配） |
| HeaderMismatchError | errors.go:65 | importer.go:194 | ✅（表头内容不匹配） |
| SheetError | errors.go:79 | importer.go:71,128 | ✅（多 sheet 错误包装） |
| MultipleSheetError | errors.go:92 | importer.go:64,136 | ✅（聚合） |
| InvalidUnmarshalError | errors.go:12 | scanner.go:297,306 | ✅（非指针/非 slice 目标） |
| ExcelLineError | errors.go:105 | **无触发点**（死类型） | ❌ 从未被使用 |
| LinesError | errors.go:115 | **无触发点**（死类型） | ❌ 从未被使用 |

### 2.2 错误分类判断正确性
- `ValidateHeaderError.IsSheetNotExistError()`（errors.go:40-42）：用 `errors.As(v.Err, &excelize.ErrSheetNotExist{})`，但 `newValidateHeaderError`（errors.go:48-50）只在 `i.reader.GetHeader` 返回 error 时包装——GetHeader 底层 `f.Rows(name)` 对不存在的 sheet 返回 `excelize.ErrSheetNotExist`？需验证（当前无测试覆盖）。若 `GetHeader` 返回的 err 不是 `ErrSheetNotExist` 指针，`IsSheetNotExistError` 恒 false，`IsSheetNotExistError` 方法就是死方法。
- **真 bug：`IsLengthError` 恒返回 false**。根因是 `errors.As` 的值/指针匹配方向：
  - `newHeaderLengthError` 返回 `&HeaderLengthError{}`（**指针**，errors.go:61），而 `IsLengthError` 的 target 是 `&HeaderLengthError{}`（**指向值类型**，errors.go:37）。Go 语义：**指针 error 不能赋值给值类型 target**，所以 `errors.As(指针err, &值类型{})` 恒 false → `IsLengthError()` 恒 false，表头长度不匹配时用户无法通过该方法识别错误。
  - 对照组 `IsMismatchError` **正常工作**：`newHeaderMismatchError` 返回值 `HeaderMismatchError{}`（errors.go:76），target 是值类型 `&HeaderMismatchError{}`（errors.go:45），值 error + 值 target 匹配成功。
  - 实测（包内临时测试）：`lengthErr` dynamic type = `*excelize.HeaderLengthError`，`IsLengthError()` = false；`mismatchErr` dynamic type = `excelize.HeaderMismatchError`，`IsMismatchError()` = true。

## 3. 资源泄漏（结合 Close 清单）

### 3.1 正常路径
- 导入：`Import`/`ImportConcurrent` 都有 `defer i.Close()`（importer.go:42,84）→ `reader.close()` → `_ = r.file.Close()`。✅ 正常路径释放。
- 导出：`Export`（exporter.go:18）**无 defer ex.Close()**，依赖调用方手动 Close。readme 示例展示调用方 `defer exporter.Close()`，**但库未兜底**。若用户忘记 defer，excelize.File（内存态）不落盘释放，泄漏的是内存文件对象。

### 3.2 错误路径
- 导入：`defer i.Close()` 覆盖所有 error 返回（`resolveSheetName`/`imp`/scan 失败都触发 defer）。✅
- 导出：`Export` 中 `createSheet`（50）、`GetRows`（38）、`SaveAs`（47）任一 error 时直接 return，**无 Close**。调用方若用 defer 可兜底，但库自身错误路径不释放。❌ 泄漏风险。
- `GetHeader` 的 rows.Close（reader.go:68-72）：defer + 错误并入返回值，是唯一标准写法。✅

### 3.3 multipart.File 所有权（NewImporterAsFile）
- `newReader`（reader.go:24-31）`excelize.OpenReader(file)` 读取后，调用方传入的 multipart.File **不在库内 Close**（库只关内部的 excelize.File）。所有权在调用方，readme 未说明释放责任，属文档盲区（非 bug，但应文档化）。

## 4. 核心正确性结论
- **真 bug 候选**：
  1. `resolveSheetName` 静默回退（reader.go:123-126）——sheet 名拼错被静默导入到首 sheet。
  2. `ConvertToType` 类型不匹配静默填零值 + 未知类型可能 panic（scanner.go:16-38, 142-143）。
  3. `IsLengthError` 恒 false（errors.go:36-37 vs 61，指针 err + 值 target 不匹配）——表头长度不匹配时无法通过该方法识别（`IsMismatchError` 对照组正常）。
- **死代码**：ExcelLineError/LinesError 全库无引用，encoding 字段无引用。
- **资源管理不对称**：导入自动 defer，导出依赖调用方。
