## P0（正确性 bug + 低成本高收益性能点）

### P0-1：resolveSheetName 静默回退掩盖"用户显式 sheet 名拼错"
- 维度：正确性
- Location：reader.go:123-126
- 问题描述：`resolveSheetName` 对"name 非空但 sheet 不存在"一律静默回退到 `firstSheetName()`。实测确认：TestImport 依赖此回退——`[]TextColumnRow` 无 WithSheetName，默认 name="Sheet1"，而 `全量字段.xlsx` 首 sheet 是「文本类字段」，靠回退才对。因此回退本身承载了"default 指任意首 sheet"的语义，不能简单删除。**真正的漏洞**是：当用户通过 `WithSheetName` 显式返回了一个非默认、非空的 sheet 名却拼错时，`resolveSheetName` 无法区分"故意的 default 回退"与"显式名拼错"，会静默导入到首 sheet 而非报错，错数据难排查。
- 建议方案：仅在"name 由 WithSheetName 显式提供且 ≠ defaultSheetName"且 sheet 不存在时返回 `excelize.ErrSheetNotExist`；保留 default name（"Sheet1"）不存在时的首 sheet 回退。
- 风险与影响面：改动 resolveSheetName 需传递"name 是否显式"的信号（当前签名仅收 name string），波及 importer 的调用点；default 回退语义保留，仅收紧显式名场景。
- 兼容性判定：兼容（default 场景行为不变，仅显式名拼错场景从静默回退改为报错）。
- 数据支撑：无需（正确性类）。已实测：`全量字段.xlsx` sheets=[文本类字段...]，TestImport 依赖 default→首 sheet 回退。

### P0-2：IsLengthError 恒返回 false（表头长度不匹配无法通过判定方法识别）
- 维度：正确性
- Location：errors.go:36-37（配合 errors.go:60-61）
- 问题描述：`newHeaderLengthError` 返回 `&HeaderLengthError{}`（**指针**，errors.go:61），但 `IsLengthError` 的 target 是 `&HeaderLengthError{}`（**指向值类型**，errors.go:37）。Go 的 `errors.As` 语义下，指针 error 不能赋值给值类型 target，故 `errors.As(指针err, &值类型{})` 恒 false，`IsLengthError()` 恒返回 false，表头长度不匹配时用户无法通过该方法识别错误类型。对照组 `IsMismatchError` 正常工作：`newHeaderMismatchError` 返回值类型 `HeaderMismatchError{}`（errors.go:76），target 值类型，值 err + 值 target 匹配成功。
- 建议方案：统一构造函数与判定方法的值/指针一致——方案 A：`newHeaderLengthError` 改为返回 `HeaderLengthError{}`（值，errors.go:61），使值 err + 值 target 匹配；方案 B：`IsLengthError` 的 target 改为指针（`var e *HeaderLengthError; errors.As(v.Err, &e)`）。推荐方案 A（内部构造函数，无 API 影响，与 `newHeaderMismatchError` 的返回值风格对齐）。
- 风险与影响面：errors.go 内部；`newHeaderLengthError` 返回类型从指针改值会影响 `newValidateHeaderError` 包装（需验证 HeaderLengthError 的其他用法，当前仅 importer.go:187 与 IsLengthError 引用）。
- 兼容性判定：兼容（内部构造函数 `newHeaderLengthError` 未导出，返回值类型调整不改任何已导出 API 签名）。
- 数据支撑：无需（正确性类）。实测（包内临时测试）：`lengthErr` dynamic type = `*excelize.HeaderLengthError`，`IsLengthError()` = false；`mismatchErr` dynamic type = `excelize.HeaderMismatchError`，`IsMismatchError()` = true。

### P0-3：TypeConverter 类型不匹配静默填零值 + 未知类型可能 panic
- 维度：正确性
- Location：scanner.go:16-38（ConvertToType）、scanner.go:142-143（applyFieldRule 的 Set）
- 问题描述：`cast.ToInt("abc")` 静默返回 0、`cast.ToBool(nil)` 静默 false，类型不匹配被吞成零值无提示；default 分支对未知类型（如 time.Time、自定义 struct）一律 `cast.ToString` 返回 string，`fieldValue.Set(string)` 到非 string 字段会 panic。
- 建议方案：ConvertToType 前先做类型可赋值性检查（reflect 类型匹配），不匹配返回带字段名+期望类型+实际值的错误；对确需宽松转换的标量类型保留 cast，但兜底分支不再盲目 ToString，改为返回明确错误。
- 风险与影响面：所有导入的字段赋值路径；行为从"静默填零值"变为"报错"，可能让原本靠零值导入的脏数据场景暴雷（需评估是改进还是破坏）。
- 兼容性判定：兼容（错误路径增强，正常匹配数据的导入不受影响；脏数据处理行为变化需在文档说明）。
- 数据支撑：无需（正确性类）。已实测 `cast.ToInt("abc")==0`、`cast.ToBool(nil)==false`。

### P0-4：scanSlice 每行重复 parse(target)，字段元数据无缓存（低成本高收益）
- 维度：性能
- Location：scanner.go:76-99（fillStruct 的 parse 调用，经 scanSlice:332 每行触发）
- 问题描述：`fillStruct` 每行调用 `parse(target)`（scanner.go:77），parse 反射遍历 struct 字段 + 解析 tag，无缓存。10 万行时重复反射 10 万次。
- 建议方案：按 `reflect.Type` 缓存 parse 结果（`sync.Map` 或 map[reflect.Type][]field），首次解析后复用；header→index 建 map 替代内层线性查找（O(字段×表头)→O(字段)）。
- 风险与影响面：scanner/FieldMapper 内部；需注意并发安全（ImportConcurrent 多 goroutine 共用 FieldMapper 时 parse 可能并发调用）；字段缓存键用 reflect.Type 需确保类型相同语义一致。
- 兼容性判定：兼容（纯内部实现优化，不改 API/标签）。
- 数据支撑：BenchmarkFillStruct 1e5 行 199ms/194MB/330万 allocs（单行 33 allocs 中 parse 反射是主要来源）；BenchmarkImport 1e5 行 3.82s/366 allocs per 行（parse+GetRows 叠加）。缓存后可降低单行 alloc。

## P1（代码质量：吞错、重复代码、死代码）

### P1-1：reader.close 吞错 `_ = r.file.Close()`
- 维度：代码质量
- Location：reader.go:93
- 问题描述：`_ = r.file.Close()` 静默丢弃 Close 错误，违背项目"不得吞错"规则（backend.md）。
- 建议方案：`Close()` 返回 error，由 importer.Close 传播；或至少记录日志。参考 `GetHeader` 的标准写法（reader.go:68-72 把 closeErr 并入返回值）。
- 风险与影响面：Importer.Close() 签名现为无返回（importer.go:34），若改为有返回是 API 变化，需评估；保守方案是内部记录。
- 兼容性判定：兼容（若保持 Close 无返回，内部记录；若改签名则 breaking，需供 v2，倾向兼容方案）。
- 数据支撑：无需（代码质量类）。

### P1-2：Import/ImportConcurrent 双份分发重复代码
- 维度：代码质量
- Location：importer.go:41-148（default 分支 50-62 vs 91-104 逐行重复；WithMultipleSheets 分支 64-73 vs 110-131）
- 问题描述：两个入口的 `switch f := e.(type)` default 分支（WithSheetName 断言 + resolveSheetName + imp）逻辑逐行重复，sheet 名解析（WithSheetName 覆盖 map key）也重复。
- 建议方案：抽 `i.importSingle(e Excel)` 与 `i.sheetNameFor(e, defaultName)` helper，两入口共用，消除重复。
- 风险与影响面：importer.go 内部重构；并发分支的 goroutine 闭包捕获需注意 name 变量遮蔽（当前用 `name := n` 局部变量规避）。
- 兼容性判定：兼容（纯内部重构）。
- 数据支撑：无需。

### P1-3：ExcelLineError / LinesError 死类型 + errors.go 注释掉代码
- 维度：代码质量
- Location：errors.go:105-130（ExcelLineError/LinesError 全库无引用）、errors.go:112（注释掉的 Error 实现）
- 问题描述：`ExcelLineError`/`LinesError` 全库无任何引用（grep 验证），`ExcelLineError.Line` 字段 + 注释掉的行号拼接逻辑是死代码。

- 风险与影响面：删除已导出类型 ExcelLineError/LinesError 属 API 删除（breaking）——需确认无外部使用者，若保守则保留但补文档或实现。
- 兼容性判定：需供 v2 决策（删除导出类型是 breaking；若仅注释说明则兼容）。
- 数据支撑：无需。

## P2（方向性改进，达门槛者）

### P2-1：Functional Options 减少导出配置样板
- 维度：使用优雅性
- Location：exporter.go:50-78（createSheet 的多个 With* 接口分派）
- 问题描述：导出 sheet 需逐一实现 WithStyles/WithColumnWidths/WithDataValidation 接口，样板 30-60 行。
- 建议方案：新增 `NewExporterWithOptions(path, WithStyle(...), WithDataValidation(...))` 或导出 option 类型，叠加到现有接口范式。
- 风险与影响面：新增 API 面 + option 类型。
- 兼容性判定：兼容（新增构造函数，不破坏 NewExporter/Export）。
- 数据支撑：样板减少约 40-60%（估）。

### P2-2：减少调用样板 helper
- 维度：使用优雅性
- Location：exporter.go writeData / excel.go 接口层
- 问题描述：简单导出场景（只有数据无样式）仍需手写结构体 + 实现 Sheets/Headers/Rows。
- 建议方案：提供 `NewSheet(headers, rows)` 之类的 helper，自动包装。
- 风险与影响面：新增 helper API。
- 兼容性判定：兼容。
- 数据支撑：样板减少约 50-70%（估）。

### P2-3：流式/迭代器导入（内存收益）
- 维度：使用优雅性（也含性能）
- Location：scanner.go:304-338（scanSlice 全量 GetRows）
- 问题描述：Import 全量加载，10 万行 B/op 1.73GB，峰值内存高。
- 建议方案：新增 `ImportStream`（逐行 yield），峰值内存降到 O(字段)。
- 风险与影响面：reader 生命周期 + skip/relation 语义重构。
- 兼容性判定：兼容（新增 API）；但涉及 reader 重构，标注供 v2 参考。
- 数据支撑：BenchmarkImport 1e5 行 B/op 1.73GB（全量加载内存证据）。

### P2-4：泛型强类型 API（type safety 收益）
- 维度：使用优雅性
- Location：importer.go:41 Import(e Excel)、excel.go:9 空接口
- 问题描述：Import 用 interface{} + reflect，无编译期类型检查；scanSlice 反射热路径。
- 建议方案：`ImportOf[T any](&e []T)` 提供编译期类型检查。
- 风险与影响面：新增泛型 API；核心 scanSlice 反射仍在（标签解析需 reflect）。
- 兼容性判定：需供 v2 决策（泛型化 Import 签名 breaking，新增 ImportOf 可兼容）。
- 数据支撑：BenchmarkScanSlice 1e5 行 2.36s（反射热路径证据，但泛型只能消入口层 interface{}，核心反射不可免——收益需谨慎估计）。
