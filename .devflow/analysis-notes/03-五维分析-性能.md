# M3 素材：性能维度分析（数据绑定）

> 数据来源：`benchmark_test.go`，`go test -bench -benchmem -benchtime=3x -count=3`，环境 Apple M2 (arm64), go1.26.4 darwin/arm64（go.mod 声明 1.23.3，差异注明）。

## 热点定位（代码→benchmark 绑定）

### 热点 1：scanSlice 的 rv.Grow(1)/SetLen 逐行扩容（scanner.go:326-331）
- 代码：`if i >= rv.Cap() { rv.Grow(1) }` + `if i >= rv.Len() { rv.SetLen(i + 1) }`，每行精确 grow 1。
- benchmark：BenchmarkScanSlice 3 档数据（见下）。
- 量级：Grow(1) 每次可能在底层触发 realloc（当 i 追平 cap 时），10 万行会经历多次底层扩容（Go slice 增长曲线）。但 grow 触发条件 `i >= rv.Cap()` 使得 cap 按需翻倍，实际 realloc 次数为 O(log N) 而非 O(N)。真正的分配大头在 GetRows 返回的 string 切片。

### 热点 2：fillStruct 嵌套 O(字段×表头) 循环 + 每行重复 parse（scanner.go:76-99）
- 代码：外层 `for _, fieldSpec := range fields`，内层 `for i, header := range headers` 线性查找列名；且 **`fields, err := parse(target)` 在每行都被重新调用**（scanner.go:77），parse 内部反射遍历 struct field + 解析 tag，没有缓存字段元数据。
- benchmark：BenchmarkFillStruct 3 档数据。
- 量级：每行 8 字段 × 8 表头的 O(64) 查找 + 每次 parse 的反射开销。字段元数据 cache（按 reflect.Type 缓存 parse 结果）是明确优化点。

### 热点 3：writeData 逐行 SetSheetRow（exporter.go:120-135）
- 代码：`for i, row := range rows { ex.f.SetSheetRow(name, fmt.Sprintf("A%d", i+1), &row) }`，每行一次 SetSheetRow 调用 + fmt.Sprintf 分配。
- benchmark：BenchmarkExport 3 档数据。
- 量级：fmt.Sprintf("A%d") 每行一次字符串格式化分配；excelize 的 SetSheetRow 逐行写入是底层库的固有成本，但本库可减少 Sprintf 开销（用 strconv.Itoa）。

### 热点 4：RelationResolver 全量缓存子表（scanner.go:174-197）
- 代码：`getChildData` 对每个 sheetName 只缓存一次（`rr.cache[sheetName]`），但**首次访问时对整个子表做一次 scanSlice 全量加载**，且 `matchSliceRelation`（scanner.go:226-239）对每个主表行 O(子表行数) 线性扫描匹配。
- benchmark：BenchmarkRelation 3 档数据。
- 量级：主表 N 行 × 子表 M 行 的 O(N×M) 匹配，10 万主表 × 100 子表 = 1000 万次比较。

## 待测项（无 benchmark 数据，不得进建议清单）

2. 内存增长曲线的非线性劣化点（需更细的规模档位采样，如 1e3/1e5/2e5）。

### 关键换算（单行成本）

- Import 单行 allocs ≈ 366 次（1e5 行），B/op ≈ 17.3KB/行 —— 反射映射 + string 切片解析的巨大分配。
- FillStruct 单行 = 33 allocs（3300/100 行，或 3300000/100000 行 = 33），B/op = 1.94KB/行。**FillStruct 单行仅 33 次 alloc，但 Import 全链路单行 366 次 alloc**——差值 ~333 次/行来自 `reader.GetRows`（excelize 底层逐 cell 解析 string 切片）+ `parse` 每行重复反射。
- ScanSlice 单行 ≈ 265 allocs，介于 GetRows（大头）与 FillStruct（小头）之间，符合"scanSlice = GetRows + FillStruct 逐行"的构成。
- Import 端到端 3.82s vs ScanSlice 2.36s：差异 ~1.4s 是文件 open/close + resolveSheetName + defer 等固定开销，10 万行摊销后占比 ~37%。

### 性能维度结论（关键发现）

1. **Import 与 ImportConcurrent 单 sheet 下几乎无差异**（3.82s vs 3.82s）：并发入口的 default 分支与串行一致，并发只在多 sheet 分支才有意义。当前 benchmark 只覆盖单 sheet，并发收益未量化（待测项）。
2. **每行 366 次 alloc 是导入性能瓶颈**，其中 fillStruct 只占 33 次（9%），其余 ~333 次来自 GetRows 的底层 string 解析与 parse 重复反射。核心优化点：`scanSlice` 每行重新 `parse(target)`（scanner.go:77/332）→ fillStruct 内 `parse` 未按 reflect.Type 缓存。
3. **fillStruct 嵌套 O(字段×表头) 查找**（scanner.go:84-91）：8 字段 × 8 表头，虽是小常数但叠加 parse 反射，可 cache 字段元数据 + 建 header→index map 降到 O(字段)。
4. **writeData 的 fmt.Sprintf("A%d") 每行分配**（exporter.go:131）：用 strconv.Itoa + 预分配列名的 buffer 可省。
5. **RelationResolver.matchSliceRelation O(主×子)**（scanner.go:226-239）：主 10 万 × 子 100 = 1000 万次 getStringFieldValue 反射调用，是 relation 慢路径主因；Relation 1e5 行 732ms 但仅主 10 万行就 6.01M allocs。
