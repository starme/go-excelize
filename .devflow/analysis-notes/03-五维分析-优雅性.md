# M3 素材：使用优雅性维度分析

## 现有用法基线（接口约定式）

从 readme + importer_test.go 提取"现有样板"：

```go
// 导入：定义结构体（带 xlsx: 标签）+ 传递指针
type TextColumnRow struct {
    Code string `xlsx:"name:字段编码"`
    ...
    Dimension []string `xlsx:"name:所属维度;split:|"`
}
var e []TextColumnRow
importer, _ := NewImporterAsPath(ctx, path)
importer.Import(&e)

// 导出：定义结构体 + 实现多个接口
type export struct{}
func (e export) Sheets() map[string]Sheet { return map[string]Sheet{...} }
func (e export) Headers() []interface{} { return ... }
func (e export) Rows() [][]interface{} { return ... }
func (e export) Style() map[string]Style { return ... }
func (e export) DataValidation() map[string]DataValidate { return ... }
```

样板成本：一个导出结构体需实现 3-5 个接口方法（Sheets/Headers/Rows/Style/DataValidation），约 30-60 行样板代码；`Excel`/`Rows`/`Sheet` 全是空 `interface{}`，无编译期类型检查。

## 五个方向逐一评估

### 方向 1：Functional Options
- **现有**：导出 sheet 结构体需逐一实现 `WithStyles`/`WithColumnWidths`/`WithDataValidation` 接口。
- **提议**：`NewExporter(path, WithStyle("A", style), WithDataValidation("A", dv))` 用 option 函数配置。
- **收益**：把"实现接口方法"降为"传 option 参数"，样式/列宽/验证配置的样板量可减少约 40-60%（尤其对只有 1-2 项样式的场景）。
- **成本**：新增 option 类型与 `NewExporter` 变长参数（或新构造函数），与现有"接口约定"范式可叠加（不破坏）。
- **兼容性**：兼容（新增 `NewExporterWithOptions` 或变长参数，老 `NewExporter` 签名若用变长参数扩容是 breaking，需新增独立构造函数）。
- **判定**：达门槛候选（样板减少 ≥30% 且可叠加），可进建议清单 P2。

### 方向 2：Builder 模式
- **现有**：一次性 `Export(e)`，无中间态。
- **提议**：`exporter.WithHeader(...).WithRows(...).Write()` 链式。
- **收益**：链式可读性提升有限，因导出配置本身不复杂。
- **成本**：新增 Builder 类型 + 运行时能力，与现有 `Export(e)` 重复。
- **兼容性**：兼容（新增 Builder）。
- **判定**：收益 < 成本，样板减少不足 30%，标注"供 v2 参考"，**不进主推**。

### 方向 3：流式 / 迭代器导入
- **现有**：`Import(&e)` 全量加载到切片，`scanSlice` 一次性 `GetRows` 全量读入内存。
- **提议**：逐行 yield（`iter.Seq` 或回调），大文件可边读边处理，峰值内存从 O(N×字段) 降到 O(字段)。
- **收益**：十万级行内存占用显著下降（benchmark 显示 10 万行 import B/op≈1.7GB，全量加载）。
- **成本**：新增流式 API 面，需处理 reader 生命周期与 skip/relation 语义。
- **兼容性**：兼容（新增 `ImportStream`，老 `Import` 保留）。
- **判定**：达门槛候选（内存收益实质量化），进建议清单 P2，标"供 v2 参考"（因涉及 reader 重构）。

### 方向 4：泛型强类型 API
- **现有**：`Import(e Excel)` 用 `interface{}` + `reflect`，运行时类型断言，无编译期类型检查。
- **提议**：`Import[T any](&e []T)` 用 Go 1.23 泛型，减少 `interface{}` 与 reflect 开销。
- **收益**：编译期类型检查 + 减少 reflect（`scanSlice` 的 reflect 热路径是性能瓶颈，benchmark 支撑）。
- **成本**：与 `xlsx:` 标签反射机制需共存（标签解析仍要 reflect），泛型只能消掉入口层的 `interface{}`，核心 scanSlice 的 reflect 仍不可免；`Import` 签名从 `Import(e Excel) error` 改泛型是 **API breaking**（或新增 `ImportOf[T]` 新函数）。
- **兼容性**：需供 v2 决策（泛型化 `Import` 签名 breaking；新增 `ImportOf[T]` 可兼容）。
- **判定**：达门槛候选（类型安全收益实质），但 breaking，标"供 v2 决策"，**不进主推**。

### 方向 5：减少调用样板
- **现有**：用户需手写结构体 + 实现多个接口。
- **提议**：提供 helper（如 `NewSheet(headers, rows)` 直接包装，或从 `[]struct` 自动反射生成 Headers/Rows）。
- **收益**：对"只有数据、无样式"的简单导出场景，样板可减少约 50-70%。
- **成本**：新增 helper API，需明确与现有接口范式的边界。
- **兼容性**：兼容（新增 helper，不破坏接口）。
- **判定**：达门槛候选，进建议清单 P2。

## 优雅性维度结论
有优化空间，但集中在"新增可选中低样板 helper（方向 1/5）"+"流式导入（方向 3）"三条有效路径；Builder（方向 2）收益不足；泛型（方向 4）收益实质但需 v2。主推 P2：方向 1、5（兼容），方向 3、4 标"供 v2 参考/决策"。
