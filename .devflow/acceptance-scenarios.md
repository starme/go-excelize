# 验收场景表

> 派生自 `docs/prd-optimization-analysis.md` §7 验收标准（9 条 P0 + 4 条 P1 + 1 条 P2）。
> 每条场景 = 场景描述 + 检查方式 + 通过判定。

---

## P0（必须全部 PASS 才算验收通过）

### 场景 P0-1 — 交付物位置
- **场景描述**：分析报告已产出，位于约定路径。
- **检查方式**：确认 `docs/optimization-analysis.md` 存在且内容非空。
- **通过判定**：文件存在于 `docs/optimization-analysis.md` 且为唯一正式交付物（不含库源码改动）。

### 场景 P0-2 — 建议清单完整性与分组
- **场景描述**：报告含"优化建议清单"，按 P0/P1/P2 分组，每条覆盖全部必填字段。
- **检查方式**：核对清单分组结构 + 逐条核对字段（ID/维度/优先级/Location/问题描述/建议方案/风险与影响面/兼容性判定，性能类加数据支撑）。
- **通过判定**：清单按优先级分组；每条至少含 8 个必填字段，性能类含"数据支撑"；无字段缺失。

### 场景 P0-3 — Location 精确性与范围归属
- **场景描述**：每条建议的 Location 精确到文件:行（或函数名），且文件属于 §4 范围源文件。
- **检查方式**：逐条将 Location 与源码比对，确认行号真实、文件在 §4 范围内。
- **通过判定**：全部 Location 真实存在、行号对应正确、文件属 §4 范围（不指向 test 夹具或 readme 之外）。

### 场景 P0-4 — 性能结论绑定 benchmark 数据
- **场景描述**：性能维度每个结论均有 benchmark 数据支撑（方法 + ≥3 档规模实测），无数据支撑的观察列"待测项"，不进入建议清单。
- **检查方式**：核对性能类建议是否有数据支撑字段；核对 §3.1 是否有 3 档（1e2/1e4/1e5）ns/op、B/op、allocs 实测数据；反向检查是否存在无数据支撑的性能断言。
- **通过判定**：性能建议均绑定数据；3 档规模实测齐全；无数据支撑的性能观察被正确归类为"待测项"。

### 场景 P0-5 — 兼容性判定无留空
- **场景描述**：每条建议兼容性判定明确为"兼容"或"需供 v2 决策"。
- **检查方式**：逐条核对兼容性判定字段，确认非空且语义明确。
- **通过判定**：全部建议（P0+P1+P2 共 13 条）兼容性判定非空。

### 场景 P0-6 — readme 差异三元组
- **场景描述**：API 设计维度 readme 差异清单每条为"readme 宣称 → 实际行为 → 判定"三元组。
- **检查方式**：逐条核对差异清单是否含三元组，并与 readme 原文、源码实际签名比对真实性。
- **通过判定**：每条差异含三元组；抽查关键条目（Style/DataValidation/Collection/NewImporterAsPath）与源码实际一致。

### 场景 P0-7 — 资源泄漏覆盖正常+错误路径
- **场景描述**：正确性维度资源泄漏分析覆盖正常路径与错误路径，每个 Close/defer 点标注文件:行。
- **检查方式**：核对 §3.4 资源泄漏表格，确认覆盖 Import/ImportConcurrent 正常+错误路径、reader 的 Close/defer、exporter 的错误路径缺口，每处标注行号。
- **通过判定**：正常+错误路径均覆盖；每个 Close/defer 点标注文件:行。

### 场景 P0-8 — 无库源码改动
- **场景描述**：报告仅"分析+建议"，不含任何库源码改动（新增 benchmark 测试文件除外）。
- **检查方式**：核对 git diff 是否无 .go 源码变更，唯一新增文件为 `benchmark_test.go`（及 docs 交付物）。
- **通过判定**：`git diff --name-only` 无库源码 .go 变更（仅新增 benchmark_test.go）。

### 场景 P0-9 — 不触及冻结契约
- **场景描述**：所有建议不修改已导出 API 签名与 xlsx: 标签语法；确需变动的单独标注"供 v2 决策"。
- **检查方式**：逐条核对涉及 API/标签改动的建议是否标注 breaking + "供 v2 决策"，且不作为主推。
- **通过判定**：无隐性破坏已导出 API/标签的建议；P1-3（删已导出类型）、P2-4（泛型）已标"需供 v2 决策"。

## P1（应当满足）

### 场景 P1-10 — 使用优雅性 5 方向全覆盖
- **场景描述**：覆盖 functional options / builder / 流式导入 / 泛型强类型 / 减少样板 5 方向，每方向含对比 + 兼容性判定。
- **检查方式**：核对 §3.5 是否 5 方向齐全，每方向有"现有用法 vs 提议用法"对比 + 收益/成本 + 兼容性判定。
- **通过判定**：5 方向齐全，每方向含对比与兼容性判定。

### 场景 P1-11 — 无第三方断言库
- **场景描述**：代码质量维度无需 testify 等第三方断言库引用。
- **检查方式**：核对 benchmark_test.go 及测试代码 import 无 testify/stretchr。
- **通过判定**：import 仅标准库 + excelize + cast，无 testify。

### 场景 P1-12 — 未删改测试夹具
- **场景描述**：未删改 `test/xxx.xlsx`。
- **检查方式**：核对 test/ 下 xlsx 夹具未变更。
- **通过判定**：test/*.xlsx 无改动。

### 场景 P1-13 — 执行摘要五维结论明确
- **场景描述**：执行摘要五个维度均给出"是否有优化空间"的明确结论（不骑墙）。
- **检查方式**：核对 §1 执行摘要表格五维度结论。
- **通过判定**：五维度均明确"有/无优化空间"。
