## 1. 背景与目标

### 1.1 业务背景

`go-excelize`（`github.com/starme/go-excelize`）是封装 `github.com/xuri/excelize/v2` 的纯 Go 库，提供基于 `xlsx:` 结构体标签的 Excel 导入/导出能力。核心链路：

- **导入**：`Importer`（`NewImporterAsPath` / `NewImporterAsFile`）→ `scanner` / `reader` → `FieldMapper` / `RelationResolver`
- **导出**：`Exporter`（`NewExporter`）把结构体切片写出为 xlsx

代码近期持续演化：`scanner.go` 经历大改（409 行变更），`reader.go` / `importer.go` 有增量修改。当前缺少一次全面体检来回答"是否值得优化、优先优化哪里"，导致后续迭代缺乏依据。

### 1.2 当前问题

- 演进过程中未做过整体盘点，模块边界、重复代码、错误处理规范可能逐步劣化
- 性能表现（导入/导出速度、内存、大文件场景）缺少量化基线
- API 设计（`xlsx:` 标签语法、接口约定式 API、readme 与实际行为）一致性未知
- 边界条件与资源管理（文件句柄 `Close`、空表、缺列、类型不匹配）未系统验证
- 使用方式（基于现有接口约定式的样板代码量）是否有更优雅的演进空间未评估

### 1.3 预期目标

本 task 的目标是**产出一份可信、可执行的分析报告**（非代码改动），用于回答一个问题并支撑后续决策：

> 当前包在性能 / 代码质量 / API 设计 / 正确性 / 使用优雅性五个维度上是否存在优化空间，优化优先级如何排序？

成功标准（可量化）：

- 一份分析报告，含**按优先级排序的优化建议清单**（P0/P1/P2）
- 每项建议字段完整（见 §6 交付物定义），Location 精确到 `文件:行`
- 性能类结论均有 benchmark 数据支撑（附基准测试方法与实测数据）
- 兼容性判定逐项给出（兼容 / 需标注供 v2 决策）
- 覆盖全部目标源文件（见 §4 范围）

## 4. 非目标（Out of Scope）

- **不实施任何优化**：不改重构、不做性能修复，仅允许新增 `*_bench_test.go` 测试文件用于数据采集（且不得修改库源码本身）；该 benchmark 文件**保留在仓库**作为可复现资产
- **不做 v2 API 重设计**：只提出方向性建议供决策（标注"供 v2 决策"），不输出具体 v2 设计
- **不新增运行时依赖**：不引入数据库 / HTTP 框架，分析建议中如涉及第三方库需标注"新增依赖"风险
- **不改动测试夹具**：`test/xxx.xlsx` 不可删改
- **不引入测试框架**：`testify` 等断言库一律不使用
- **不改动 `xlsx:` 标签语法与已导出 API**：两者为冻结契约

## 5. 分析维度与深度要求

> 本 PRD 只定义每个维度"要回答什么问题、按什么标准判定期望产出"，**不预设是否有优化空间的结论**——结论由分析报告回答。

### 5.1 性能（Performance）

**要回答的问题：**

1. 导入/导出的时间开销主要集中在哪些环节（解析、映射、写出）？是否存在可量化的瓶颈？
2. 内存占用随数据量（行数/列数）的增长曲线如何？是否存在不必要的大对象分配或全量加载？
3. 大文件（大数据量行数）场景的表现，与中等规模场景相比是否存在非线性劣化点？

**产出要求（深度标准）：**

- 建立 benchmark 基线：报告中须附**基准测试方法**（测试夹具、数据规模档位、计次规则）+ **实测数据**（每档至少一组 ns/op、alloc、bytes）
- 数据规模固定 3 档：百级 / 万级 / 十万级行，允许用新增 `*_bench_test.go` 采集，运行结果写入报告但**不修改库源码**
- 每个性能结论必须绑定具体 benchmark 数据，**不允许仅凭代码 review 断言"慢/占内存"**
- 对每个疑似瓶颈给出定位（`文件:行`）与量级评估

**判定红线：** 无 benchmark 数据支撑的性能结论不得进入建议清单，只能列入"待测项"。

### 5.2 代码质量（Code Quality）

**要回答的问题：**

1. 模块结构是否清晰？导入链路单向依赖（`Importer → scanner → reader → FieldMapper → RelationResolver`）是否被破坏？
2. 是否存在重复代码（重复的解析逻辑、重复的类型断言、重复的错误包装样板）？
3. 错误处理是否规范：错误是否统一经 `errors.go` 定义/包装、是否带列名或工作表名上下文、有无吞错（静默 `_` 丢弃返回值）？
4. `errors.go` 中 `ExcelLineError.Error()` 等存在注释掉的代码，是否存在死代码/未使用类型？
5. 可读性：命名是否表达意图、函数是否单一职责（单函数 ≤ 50 行、嵌套 ≤ 3 层）、注释是否解释 WHY？

**产出要求（深度标准）：**

- 每个问题/机会给出 `文件:行` 精确定位
- 重复代码需列出重复片段的位置与可合并判断
- 错误处理问题按 severity 分级（吞错 = 高，缺上下文 = 中，风格 = 低）

### 5.3 API 设计（API Design）

**要回答的问题：**

1. `xlsx:` 标签语法是否一致：`name:` / `split:` / `relation:` / `default:` / `-` 在导入、导出两个方向的解析是否对齐？有无"单侧支持"的标签（违反项目规则"新增标签必须双侧同步"）？
2. 导入/导出 API 是否完备：是否存在用户常见需求（如跳过表头行、多 sheet、数据验证）无 API 覆盖的缺口？
3. readme 文档与实际行为是否一致：readme 中的示例、接口方法（如 `Collection`、`Sheets()`、`SheetName()` 等）与实际实现、测试用例中的调用形态是否吻合？有无文档承诺但代码未实现，或代码实现但文档未说明？

**产出要求（深度标准）：**

- 标签语法逐项核对，输出一致性矩阵（标签 → 导入支持 / 导出支持）
- readme 与实际行为的差异清单（逐条：readme 宣称 → 实际行为 → 判定）
- API 缺口按影响面排序

### 5.4 正确性（Correctness）

**要回答的问题：**

1. 边界条件：空表、空文件、缺列、多余列、表头不匹配、类型不匹配（int/string/[]string/嵌套结构）时的行为是否正确、错误信息是否可定位？
2. 错误路径：`errors.go` 中定义的各种错误类型（`ValidateHeaderError`、`HeaderLengthError`、`HeaderMismatchError`、`SheetError`、`ExcelLineError` 等）是否被正确触发、分类是否对得上？
3. 资源泄漏：`Exporter` / `Importer` 的文件句柄（`excelize.File.Close`）是否在所有路径（含错误路径）都被正确释放？`NewImporterAsFile` 接收的 `multipart.File` 是否负责释放？

**产出要求（深度标准）：**

- 边界条件逐项给出"当前行为 + 是否 bug + 影响面"
- 资源泄漏检查覆盖**正常路径与错误路径**，每个 `Close`/defer 点标注 `文件:行`
- 疑似 bug 需给出可复现的最小用例描述（不要求写实现，但需说明触发条件）

### 5.5 使用优雅性（Usability / Ergonomics）

**维度的定义（依据 requirement_summary 补充）：**

基于**现有使用方式**——即 readme 示例与测试用例中体现的调用形态（当前是**接口约定式**：用户结构体实现 `WithSheetName` / `Headers()` / `Rows()` / `Style()` / `DataValidation()` 等接口，`Excel` / `Rows` / `Sheet` 均为空接口 `interface{}`）——探索是否存在**更优雅的新增可选用法**，评估其收益与成本。

**明确约束：**

- 只能提出"**新增可选的优雅用法**"，**不得以破坏现有用法为代价**（向后兼容是硬约束）
- 所有方向仅作为**分析方向**写入报告，本 PRD 与报告都**不预设结论**——是否值得引入由报告评估回答

**分析方向（需在报告中逐一评估可行性、样板代码减少量、类型安全增益、引入成本、兼容性）：**

| 分析方向 | 待回答的问题 |
|---------|-------------|
| Functional Options | 用 `NewExporter(path, WithStyle(...), ...)` 替代"结构体实现多个接口"是否能减少样板？对现有"接口约定"范式是否可叠加？ |
| Builder 模式 | 链式构建导出配置是否能提升可读性？ |
| 流式 / 迭代器导入 | 大文件场景下逐行 yield 是否比全量加载到 `Collection` 更合理？内存收益如何量化？ |
| 泛型强类型 API | 用 Go 1.23 泛型提供 `Import[T any]` / `Export[T]` 减少 `interface{}` + `reflect` 的运行时开销与类型断言样板？与 `xlsx:` 标签反射机制如何共存？ |
| 减少调用样板 | 当前"定义结构体 + 实现多个接口"的样板代码量能否通过可选 helper 减少？ |

**产出要求（深度标准）：**

- 每个方向必须有"现有样板代码 vs 提议用法"的对比（可用 readme/测试中的真实片段）
- 每个方向给出：收益（样板减少量/类型安全/性能）+ 成本（实现复杂度/新增 API 面/学习成本）+ 兼容性判定
- 明确哪些方向值得进入建议清单，哪些仅作为"供 v2 决策"的方向性备注
- **进主推清单的门槛**：样板代码减少 ≥30%，或类型安全/性能有实质提升；未达门槛的方向标注"供 v2 参考"，不进主推清单

## 8. 风险与约束

### 8.1 兼容性红线（冻结契约）

- 已导出 API（`NewImporterAsPath` / `NewImporterAsFile` / `NewExporter` 等）签名**不可 breaking change**
- `xlsx:` 标签语法**只能追加**，不能删改；结构体标签中的中文列名是面向最终用户的表头文案，改动视为 breaking change
- 所有建议默认给兼容方案；确需 breaking 的单独标注"供 v2 决策"，且不作为主推

### 8.2 定位约束

- 纯库项目：不引入数据库 / HTTP 等运行时依赖
- 新增第三方依赖必须在建议中标注"新增依赖"风险（当前直接依赖仅 `spf13/cast`、`xuri/excelize/v2`）

### 8.3 测试约束

- 测试统一标准库 `testing` + `reflect.DeepEqual`，禁用 `testify`
- 测试写在被测文件同目录同名 `_test.go`，包名 `excelize`（包内测试）
- 测试夹具 `test/xxx.xlsx` 不可删改

### 8.4 数据采集边界

- 本 task 允许新增 `*_bench_test.go` 用于性能数据采集，但**不得修改库源码**、不得修改 `defer`/`Close` 语义以影响测量
- `*_bench_test.go` **保留在仓库**，作为可复现资产供后续优化 task 复测对比基线；不得在本次 task 结束后删除
- benchmark 数据作为报告证据，不得据此在本次 task 内实施任何性能修复

### 8.5 风险清单

| 风险 | 影响 | 应对 |
|------|------|------|
| benchmark 数据受环境噪声影响，结论不稳 | 性能结论可信度下降 | 报告中注明测试环境（Go 版本 / 机器）、采用多次计次取稳定值 |
| 分析报告结论与实际代码漂移（代码持续演化） | 建议失效 | 每条建议绑定 `文件:行`，便于失效时定位 |
| "使用优雅性"方向过度设计 | 引入超出实际需求的 API | 每个方向必须给出"收益 vs 成本"量化评估，**未达门槛（样板减少 <30% 且无类型安全/性能实质提升）的标注"供 v2 参考"，不进主推清单** |
